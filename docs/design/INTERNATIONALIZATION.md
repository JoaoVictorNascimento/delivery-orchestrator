# Internationalization

Approved locales: `en-US` (default/fallback) and `pt-BR`. Header uses shadcn Select with SVG flags and explicit accessible language names: US English, Brazilian Portuguese. Never use a language switch or flag-only control. Persist locale locally, change immediately without reload or loss of route/selection. Support keyboard focus, list navigation and announcements. Flags decorative when name is present.

Use i18next + react-i18next + i18next-icu and Intl API; browser detection may be offered as an initial preference only, with English fallback and explicit override. Namespace per domain: common, navigation, overview, deliveries, action-center, executions, findings, pipelines, knowledge, ai-usage, agents, projects, integrations, insights, settings. Typed keys and parity tests; no hardcoded UI strings or string concatenation for grammar/plurals. Map domain status/error codes to translation keys; do not localize identifiers on the wire. Format dates, numbers, units, durations, percentages and chart axes consistently; timezone explicit.

Translate menus, labels, statuses, severities, workflow steps, forms, validation/errors, empty/loading/stale states, tooltips, charts, exports' human labels, notifications and accessibility labels. Preserve source logs, comments, commit hashes/messages, branch/file names, commands, JSON keys and technical IDs. Generated reports and agent explanations have independent language configuration; commit, MR and report defaults may be overridden per project. Do not silently translate evidence or mutate it. Public documentation remains English.

Acceptance: locale key parity and missing-key test, ICU plurals, locale-sensitive formatting, screenshot/manual review in both locales/themes, longer Portuguese text without clipping, accessible select, persisted preference across reload. Unified prototype must apply this consistently to all 13 screens. Earlier independent HTML prototypes may only approximate these requirements.
